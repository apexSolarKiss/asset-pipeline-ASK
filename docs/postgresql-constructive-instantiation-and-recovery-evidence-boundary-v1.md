## What was tested

Milestone 15's next-evidence condition named a **materially different second target** — different affordances than the filesystem target — before any consuming-grammar talk. Its accepted consumer evidence was bounded to one known-achievable filesystem target ([`docs/package-instantiation-consumer-evidence-boundary-v1.md`](package-instantiation-consumer-evidence-boundary-v1.md)).

PostgreSQL is materially different in the way that condition intends. It is not another filesystem representation: it is a typed, relational, constraint-bearing target whose affordances pressure exactly the source-depth and authorization distinctions the definition layer exists to preserve. A frozen portable asset-definition package — the proven 2c marketing-hero instance `PKT-MSG-HG-001`, fixed by fixture hash before any load script was emitted — was instantiated as **one concrete relational representation** in a real PostgreSQL 17.11 database, verified against the fixture, queried across twelve recovery surfaces, exported, and handed to a fresh reader for recovery.

**What this run was, exactly.** An executor-authored prototype representation, built from the architecture attempt and a design checklist, followed by one **instruction-isolated assisted-recovery** pass. It was **not** a repetition of the formally calibrated package-instantiation planning consumer on a second target. That distinction is load-bearing for everything below: the target-diversity question was exercised; the consumer-repetition question was not.

**Recovery-pass boundary.** The reader's task-specific file inputs were two exports and a recovery prompt. The source YAML, the architecture attempt, the controller / contract artifacts, the adjudication, and the build's own findings relation were withheld. The export itself, however, deliberately carried AP-derived lifecycle assignments, carrier-provenance classifications, and explanatory comments; and ambient project instruction and memory-index context existed in the reader's runtime. The pass therefore demonstrates **assisted recovery from a provenance-rich representation** — not context isolation, prior non-exposure, or blind-reader evidence.

## What held (the earned claim)

> One frozen package was concretely instantiated in PostgreSQL, its tested source semantics were preserved and recoverable through one instruction-isolated assisted-recovery pass, and no target incompatibility was established. This is bounded evidence from one package and one relational representation — not a canonical schema, consuming grammar, converter, validator, runtime, general PostgreSQL-compatibility claim, or all-package portability claim.

Supported by: one concrete PostgreSQL representation; a verification suite reporting `160 passed · 0 failed` at exit 0 with an empty failure list; twelve executed recovery surfaces evidenced by query output rather than by schema capability; and one assisted-recovery pass carrying the context limitations stated above.

## Durable findings

```text
1. aggregate candidate evidence remained aggregate;
2. descriptor-depth selection was not inflated into an entity;
3. selection remained distinct from governance;
4. AP-derived lifecycle interpretation remained visibly interpretive;
5. source absence and insufficiency were preserved rather than silently filled;
6. no source meaning was found flattened or overwritten on the tested surfaces;
7. no target incompatibility was established;
8. the representation carried package→slot containment but not the
   inheritance rule that explains lawful slot-level narrowing;
9. one package remains one package.
```

Finding 8 is the sharpest and the most architectural. A packet-level aperture grant and a slot-level prompt are **not** peer competing carriers: the slot layer is role-specific narrowing within the scope / inheritance hierarchy, so a slot prompt that fixes what the packet leaves open is the inheritance working, not a contradiction. What the relational representation carried was containment (slots belong to a package) and the AP lifecycle classification. Neither states *precedence*. A reader holding only the export therefore could not separate lawful narrowing from carrier inconsistency — and did not. This is a **representation-legibility limitation**, not a defect in the package and not evidence that PostgreSQL is incompatible.

Findings 1–6 are the constructive half: the distinctions that survived are the ones the representation declined to resolve. Every place the build refused to invent structure — no candidate entities, no framing column, no structured obligation model, no enforcement semantics, no filled-in reference scope — is a place a limit was recovered instead of a fact.

Finding 7 is a capability boundary, not a compatibility result. Force labels are carried faithfully as data while no database mechanism interprets or enforces their normative meaning. Inertness is the expected condition for a target that declares no domain semantics; zero established incompatibilities does not mean PostgreSQL compatibility is proven.

## What it did NOT prove

```text
no repeatable package-instantiation consumer — the formally calibrated consumer
  was NOT re-run on target two; this was an executor-authored prototype
no consuming grammar (one package, one target, one representation, one reader)
no canonical schema · no converter · no validator · no runtime
no general PostgreSQL compatibility · no all-package portability
no blind-reader evidence — the pass was instruction-isolated, not context-isolated
no source-order invariance outside the one represented slot ordinal
```
